# Formato de archivos de flujo

## Qué define este documento

Este documento especifica el formato exacto que deben seguir los archivos de flujo para que CodeAtlas pueda leerlos, interpretarlos y representarlos visualmente.

Un flujo describe un **proceso concreto con pasos secuenciales**, no lo que muestra una pantalla. Tiene sentido crearlo cuando el proceso cruza más de una pantalla, implica llamadas entre frontend y backend, o tiene pasos con lógica relevante que vale la pena documentar.

Los flujos no pertenecen ni al frontend ni al backend — son transversales y referencian lo que necesiten de ambas capas.

---

## Reglas generales

- Cada archivo representa un único flujo.
- Todos los archivos empiezan con un bloque de frontmatter YAML delimitado por `---`.
- El frontmatter contiene los campos estructurados que el parser usa para construir el diagrama.
- Después del frontmatter van las secciones Markdown con contenido descriptivo.
- Los campos de referencia (`screens`, `modules`, `database`) usan IDs de otros archivos.
- Los IDs deben coincidir exactamente con el identificador del archivo o elemento al que apuntan.

---

## Ubicación

```
flows/{id}-flows.md
```

---

## Formato completo

```markdown
---
type: flow
id: user-login
name: User Login
description: Complete process from login form submission to dashboard access
trigger: user submits login form
screens: [login, dashboard]
modules:
  - id: auth-frontend
    file: login-view
    functions: [handleLogin]
  - id: auth-backend
    file: auth-controller
    functions: [login]
database: [users]
---

## Steps
1. User enters username and password on the login screen
2. Frontend calls POST /auth/login with the credentials
3. Backend validates credentials against the users table
4. Backend generates and returns a session token
5. Frontend stores the token and redirects to dashboard

## Error Cases
- Invalid credentials: show error message on login screen
- Server error: show generic error and stay on login screen

## Notes
Relevant technical decisions about this flow.
```

---

## Referencia de campos del frontmatter

| Campo | Tipo | Requerido | Descripción |
|-------|------|-----------|-------------|
| `type` | string | **sí** | Siempre `flow` |
| `id` | string | **sí** | Identificador único del flujo. Debe coincidir con el nombre del archivo antes de `-flows.md` |
| `name` | string | **sí** | Nombre legible del flujo |
| `description` | string | **sí** | Descripción breve en una línea |
| `trigger` | string | **sí** | Qué inicia el flujo (acción del usuario, evento del sistema, etc.) |
| `screens` | lista de IDs | no | Pantallas que participan en el flujo. Cada ID apunta a `screens/{id}-screens.md` |
| `modules` | lista simple o de objetos | no | Módulos que participan en el flujo. Puede ser una lista plana de IDs o una lista de objetos con detalle. Ver formato detallado más abajo |
| `database` | lista de IDs | no | Entidades de base de datos que se leen o modifican durante el flujo. Cada ID apunta a `database/{id}-database.md` |

---

## Formato del campo `modules`

El campo `modules` admite dos niveles de detalle:

### Simple (solo IDs de módulo)

```yaml
modules: [auth-frontend, auth-backend]
```

### Detallado (módulo + archivo + funciones)

```yaml
modules:
  - id: auth-frontend
    file: login-view
    functions: [handleLogin]
  - id: auth-backend
    file: auth-controller
    functions: [login]
```

Dentro del formato detallado:

| Campo | Requerido | Descripción |
|-------|-----------|-------------|
| `id` | **sí** | ID del módulo. Apunta a `modules/backend/{id}-backend-modules.md` o `modules/frontend/{id}-frontend-modules.md` según el sufijo |
| `file` | **sí** | ID de un archivo declarado en `files` del módulo referenciado |
| `functions` | no | Lista de nombres de funciones declaradas en ese archivo que participan en el flujo |

Ambos formatos pueden coexistir en el mismo flujo — algunos módulos pueden ir con detalle y otros solo con ID.

---

## Referencia de secciones Markdown

| Sección | Requerida | Contenido |
|---------|-----------|-----------|
| `## Steps` | **sí** | Lista ordenada de pasos del proceso de principio a fin. Debe describir qué hace el usuario, qué hace el frontend y qué hace el backend en cada paso |
| `## Error Cases` | no | Qué puede fallar en cada momento del flujo y cómo se gestiona |
| `## Notes` | no | Decisiones técnicas relevantes del flujo |

---

## Cómo funcionan las referencias

| Campo | Dónde busca el parser |
|-------|----------------------|
| `screens` | `screens/{id}-screens.md` |
| `modules[].id` (backend) | `modules/backend/{id}-backend-modules.md` |
| `modules[].id` (frontend) | `modules/frontend/{id}-frontend-modules.md` |
| `modules[].file` | Lista `files` dentro del módulo referenciado |
| `modules[].functions` | Sección `## Functions` del archivo referenciado |
| `database` | `database/{id}-database.md` |

El parser distingue si un módulo es frontend o backend por el sufijo de su ID (`-frontend` o `-backend`).

## Ejemplos según nivel de detalle

### Mínimo (solo campos obligatorios)

```markdown
---
type: flow
id: user-login
name: User Login
description: Complete process from login form submission to dashboard access
trigger: user submits login form
---

## Steps
1. User enters username and password on the login screen
2. Frontend validates the form and calls the login API
3. Backend validates credentials and returns a session token
4. Frontend redirects the user to the dashboard
```

### Medio (con referencias a pantallas, módulos y base de datos)

```markdown
---
type: flow
id: user-login
name: User Login
description: Complete process from login form submission to dashboard access
trigger: user submits login form
screens: [login, dashboard]
modules: [auth-frontend, auth-backend]
database: [users]
---

## Steps
1. User enters username and password on the login screen
2. Frontend calls POST /auth/login with the credentials
3. Backend validates credentials against the users table
4. Backend generates and returns a session token
5. Frontend stores the token and redirects to dashboard

## Error Cases
- Invalid credentials: show error message on login screen
- Server error: show generic error and stay on login screen
```

### Completo (con detalle de archivos y funciones)

```markdown
---
type: flow
id: user-login
name: User Login
description: Complete process from login form submission to dashboard access
trigger: user submits login form
screens: [login, dashboard]
modules:
  - id: auth-frontend
    file: login-view
    functions: [handleLogin]
  - id: auth-backend
    file: auth-controller
    functions: [login]
database: [users]
---

## Steps
1. User enters username and password on the login screen
2. handleLogin() validates the form and calls POST /auth/login
3. login() validates credentials against the users table
4. login() generates and returns a signed JWT token
5. Frontend stores the token in localStorage and redirects to dashboard

## Error Cases
- Invalid credentials: login() returns 401, handleLogin() shows error on screen
- Server error: login() returns 500, handleLogin() shows generic error

## Notes
Session tokens are JWT signed with HS256 and expire after 24 hours.
```
