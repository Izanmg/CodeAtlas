# Formato de archivos de flujo

> **Modificación — 2026-05-08**
> Se rediseña la representación visual de los flujos en el diagrama y el formato de la sección `## Steps`.
>
> **Qué cambia:**
> - Los pasos dejan de ser texto libre y pasan a admitir un prefijo de referencia opcional `[capa:ref]` que indica a qué nodo del diagrama pertenece cada paso.
> - Los flujos ya no se renderizan como nodos independientes en el canvas. En su lugar, aparecen como chips dentro de los nodos de las capas que tocan (backend, frontend, screen, database).
> - Se añade un **modo Flujos** en el canvas con edges direccionales entre los nodos participantes y un panel lateral con los pasos secuenciales.
>
> **Compatibilidad hacia atrás:** los archivos de flujo existentes sin prefijos en los steps siguen siendo válidos. Los pasos sin prefijo se procesan como `{ layer: null, nodeId: null }` y se muestran como texto simple en el panel, sin generar edges ni chips en nodos.

---

## Qué define este documento

Este documento especifica el formato exacto que deben seguir los archivos de flujo para que CodeAtlas pueda leerlos, interpretarlos y representarlos visualmente.

Un flujo describe un **proceso concreto con pasos secuenciales**, no lo que muestra una pantalla. Tiene sentido crearlo cuando el proceso cruza más de una pantalla, implica llamadas entre frontend y backend, o tiene pasos con lógica relevante que vale la pena documentar.

Los flujos no pertenecen ni al frontend ni al backend — son transversales y referencian lo que necesiten de ambas capas.

---

## Reglas generales

- Cada archivo representa un único flujo.
- Todos los archivos empiezan con un bloque de frontmatter YAML delimitado por `---`.
- El frontmatter contiene los campos estructurados que el parser usa para construir el diagrama.
- Después del frontmatter van las secciones Markdown con contenido descriptivo.
- Los campos de referencia (`screens`, `modules`, `database`) usan IDs de otros archivos.
- Los IDs deben coincidir exactamente con el identificador del archivo o elemento al que apuntan.

---

## Ubicación

```
flows/{id}-flows.md
```

## Formato completo

```markdown
---
type: flow
id: user-login
name: User Login
description: Complete process from login form submission to dashboard access
trigger: user submits login form
screens: [login, dashboard]
modules:
  - id: auth-frontend
    file: login-view
    functions: [handleLogin]
  - id: auth-backend
    file: auth-controller
    functions: [login]
database: [users]
---

## Steps
- [screen:login] El usuario rellena el formulario de login
- [frontend:auth-frontend/LoginView.vue] Se envían las credenciales al endpoint POST /auth/login
- [backend:auth-backend/auth.service.ts/validateToken] Se valida el token JWT
- [database:users] Se consulta el usuario en base de datos
- [backend:auth-backend/session.service.ts/createSession] Se crea la sesión
- [screen:dashboard] Se redirige al dashboard

## Error Cases
- Invalid credentials: show error message on login screen
- Server error: show generic error and stay on login screen

## Notes
Relevant technical decisions about this flow.
```

## Referencia de campos del frontmatter

| Campo | Tipo | Requerido | Descripción |
|-------|------|-----------|-------------|
| `type` | string | **sí** | Siempre `flow` |
| `id` | string | **sí** | Identificador único del flujo. Debe coincidir con el nombre del archivo antes de `-flows.md` |
| `name` | string | **sí** | Nombre legible del flujo |
| `description` | string | **sí** | Descripción breve en una línea |
| `trigger` | string | **sí** | Qué inicia el flujo (acción del usuario, evento del sistema, etc.) |
| `screens` | lista de IDs | no | Pantallas que participan en el flujo. Cada ID apunta a `screens/{id}-screens.md` |
| `modules` | lista simple o de objetos | no | Módulos que participan en el flujo. Puede ser una lista plana de IDs o una lista de objetos con detalle. Ver formato detallado más abajo |
| `database` | lista de IDs | no | Entidades de base de datos que se leen o modifican durante el flujo. Cada ID apunta a `database/{id}-database.md` |

---

## Formato del campo `modules`

El campo `modules` admite dos niveles de detalle:

### Simple (solo IDs de módulo)

```yaml
modules: [auth-frontend, auth-backend]
```

### Detallado (módulo + archivo + funciones)

```yaml
modules:
  - id: auth-frontend
    file: login-view
    functions: [handleLogin]
  - id: auth-backend
    file: auth-controller
    functions: [login]
```

Dentro del formato detallado:

| Campo | Requerido | Descripción |
|-------|-----------|-------------|
| `id` | **sí** | ID del módulo. Apunta a `modules/backend/{id}-backend-modules.md` o `modules/frontend/{id}-frontend-modules.md` según el sufijo |
| `file` | **sí** | ID de un archivo declarado en `files` del módulo referenciado |
| `functions` | no | Lista de nombres de funciones declaradas en ese archivo que participan en el flujo |

Ambos formatos pueden coexistir en el mismo flujo — algunos módulos pueden ir con detalle y otros solo con ID.

## Formato de la sección `## Steps`

Cada paso es un ítem de lista (`-`) con un prefijo de referencia opcional seguido del texto descriptivo:

```
- [capa:moduleId/archivo/función] Descripción del paso
```

### Sintaxis del prefijo

| Capa | Ejemplo | Granularidad |
|---|---|---|
| `screen` | `[screen:login]` | pantalla |
| `frontend` | `[frontend:auth-frontend/LoginView.vue]` | módulo / componente |
| `backend` | `[backend:auth-backend/auth.service.ts/validateToken]` | módulo / archivo / función |
| `database` | `[database:users]` | tabla (una o varias separadas por coma) |
| *(sin prefijo)* | *(ausente)* | paso sin nodo asignado — válido, aparece en el panel como texto simple |

Los niveles de granularidad son opcionales de derecha a izquierda:
- `[backend:auth-backend]` → solo módulo
- `[backend:auth-backend/auth.service.ts]` → módulo + archivo
- `[backend:auth-backend/auth.service.ts/validateToken]` → módulo + archivo + función

### Efecto del prefijo en el diagrama

- El parser extrae el prefijo y calcula el `nodeId` correspondiente en Vue Flow (`scr-X`, `mod-X`, `db-X`).
- Los nodos del canvas muestran un chip con el nombre del flujo si tienen al menos un paso que los referencia.
- En el **modo Flujos** del canvas, se dibujan edges direccionales entre nodos de pasos consecutivos cuando el nodo cambia. Si dos pasos consecutivos apuntan al mismo nodo, no se genera edge entre ellos.
- El panel izquierdo del modo Flujos muestra los pasos secuencialmente con su referencia (capa, archivo, función). Cuando se selecciona un nodo en el canvas, sus pasos en el flujo activo se resaltan con un borde.

---

## Referencia de secciones Markdown

| Sección | Requerida | Contenido |
|---------|-----------|-----------|
| `## Steps` | **sí** | Lista de pasos (`-`) con prefijo `[capa:ref]` opcional. Describe el proceso de principio a fin indicando qué nodo del diagrama ejecuta cada paso |
| `## Error Cases` | no | Qué puede fallar en cada momento del flujo y cómo se gestiona |
| `## Notes` | no | Decisiones técnicas relevantes del flujo |

---

## Cómo funcionan las referencias

| Campo | Dónde busca el parser |
|-------|----------------------|
| `screens` | `screens/{id}-screens.md` |
| `modules[].id` (backend) | `modules/backend/{id}-backend-modules.md` |
| `modules[].id` (frontend) | `modules/frontend/{id}-frontend-modules.md` |
| `modules[].file` | Lista `files` dentro del módulo referenciado |
| `modules[].functions` | Sección `## Functions` del archivo referenciado |
| `database` | `database/{id}-database.md` |

El parser distingue si un módulo es frontend o backend por el sufijo de su ID (`-frontend` o `-backend`).

## Ejemplos según nivel de detalle

### Mínimo (solo campos obligatorios, sin prefijos en steps)

Compatible con el formato antiguo. Los pasos aparecen en el panel como texto simple pero no generan edges ni chips en nodos.

```markdown
---
type: flow
id: user-login
name: User Login
description: Complete process from login form submission to dashboard access
trigger: user submits login form
---

## Steps
- User enters username and password on the login screen
- Frontend validates the form and calls the login API
- Backend validates credentials and returns a session token
- Frontend redirects the user to the dashboard
```

### Medio (prefijos de capa sin detalle de archivo ni función)

Los nodos relevantes muestran el chip del flujo. Se generan edges entre capas distintas.

```markdown
---
type: flow
id: user-login
name: User Login
description: Complete process from login form submission to dashboard access
trigger: user submits login form
screens: [login, dashboard]
modules: [auth-frontend, auth-backend]
database: [users]
---

## Steps
- [screen:login] User enters username and password on the login screen
- [frontend:auth-frontend] Frontend calls POST /auth/login with the credentials
- [backend:auth-backend] Backend validates credentials against the users table
- [backend:auth-backend] Backend generates and returns a session token
- [screen:dashboard] Frontend stores the token and redirects to dashboard

## Error Cases
- Invalid credentials: show error message on login screen
- Server error: show generic error and stay on login screen
```

### Completo (con detalle de archivo y función)

Máxima granularidad. El panel lateral muestra archivo y función en cada paso.

```markdown
---
type: flow
id: user-login
name: User Login
description: Complete process from login form submission to dashboard access
trigger: user submits login form
screens: [login, dashboard]
modules:
  - id: auth-frontend
    file: login-view
    functions: [handleLogin]
  - id: auth-backend
    file: auth-controller
    functions: [login]
database: [users]
---

## Steps
- [screen:login] El usuario rellena el formulario de login
- [frontend:auth-frontend/LoginView.vue/handleLogin] Se valida el formulario y se llama a POST /auth/login
- [backend:auth-backend/auth.controller.ts/login] Se validan las credenciales contra la tabla users
- [database:users] Se consulta el registro del usuario
- [backend:auth-backend/auth.service.ts/generateToken] Se genera el JWT firmado
- [screen:dashboard] Se almacena el token y se redirige al dashboard

## Error Cases
- Invalid credentials: login() returns 401, handleLogin() shows error on screen
- Server error: login() returns 500, handleLogin() shows generic error

## Notes
Session tokens are JWT signed with HS256 and expire after 24 hours.
```
