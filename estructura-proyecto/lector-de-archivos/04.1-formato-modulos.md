# Formato de archivos de módulo

## Qué define este documento

Este documento especifica el formato exacto que deben seguir los archivos de módulo para que CodeAtlas pueda leerlos, interpretarlos y representarlos visualmente.

Los archivos de módulo se dividen en dos tipos según la capa a la que pertenecen: `backend` y `frontend`. Cada tipo tiene su propio conjunto de campos y secciones.

---

## Reglas generales

- Cada archivo representa un único módulo.
- Todos los archivos empiezan con un bloque de frontmatter YAML delimitado por `---`.
- El frontmatter contiene los campos estructurados que el parser usa para construir el diagrama.
- Después del frontmatter van las secciones Markdown con contenido descriptivo.
- Todos los campos de referencia (`screens`, `database`, `consumes-api`, `depends-on`) usan IDs de otros archivos, no nombres libres.
- Los IDs deben coincidir exactamente con el identificador del archivo al que apuntan.

### Campos obligatorios y opcionales

Los campos del frontmatter marcados como obligatorios deben estar siempre presentes. El resto puede omitirse si no aplica o si no se quiere ese nivel de detalle.

Las secciones Markdown marcadas como opcionales pueden omitirse por completo sin que el parser falle.

---

## Módulo de backend

### Ubicación

```
modules/backend/{id}-backend-modules.md
```

### Formato completo

```markdown
---
type: module
layer: backend
id: auth-backend
name: Authentication
description: Handles user identity, session management and access control
database: [users]
api:
  - POST /auth/login
  - POST /auth/register
  - POST /auth/logout
  - GET /auth/me
depends-on: []
folders:
  - id: controllers
    path: src/controllers
  - id: services
    path: src/services
files:
  - id: auth-controller
    folder: controllers
    path: auth.controller.js
    type: controller
  - id: auth-service
    folder: services
    path: auth.service.js
    type: service
---

## Purpose
Explanation of what this module does and what problem it solves within the application.

## Functions

### auth-controller
- login(username, password)
- register(username, password, birthDate)

### auth-service
- validateSession(token)
- hashPassword(password)

## Notes
Relevant technical decisions or constraints for this module.
```

### Referencia de campos del frontmatter

| Campo | Tipo | Requerido | Descripción |
|-------|------|-----------|-------------|
| `type` | string | **sí** | Siempre `module` |
| `layer` | string | **sí** | Siempre `backend` para módulos de servidor |
| `id` | string | **sí** | Identificador único. Debe coincidir con el nombre del archivo antes de `-backend-modules.md` |
| `name` | string | **sí** | Nombre legible del módulo |
| `description` | string | **sí** | Descripción breve en una línea |
| `database` | lista de IDs | **sí** | IDs de entidades de base de datos que usa este módulo. Cada ID apunta a `database/{id}-database.md`. Puede ser lista vacía `[]` |
| `api` | lista de strings | **sí** | Endpoints que expone este módulo en formato `MÉTODO /ruta`. Puede ser lista vacía `[]` |
| `depends-on` | lista de IDs | **sí** | IDs de otros módulos de backend de los que depende. Puede ser lista vacía `[]` |
| `folders` | lista de objetos | no | Subcarpetas del módulo. Cada objeto tiene `id` y `path` |
| `files` | lista de objetos | no | Archivos del módulo. Cada objeto tiene `id`, `path` y `type` (tipo de archivo: `controller`, `service`, `model`, `middleware`, etc.). El campo `folder` es opcional e indica el ID de la carpeta a la que pertenece; si se omite, el archivo se considera en la raíz del módulo |

### Referencia de secciones Markdown

| Sección | Requerida | Contenido |
|---------|-----------|-----------|
| `## Purpose` | **sí** | Qué hace el módulo y qué problema resuelve |
| `## Functions` | no | Funciones del módulo. Si hay archivos definidos en el frontmatter, pueden usarse como subsecciones (`### id-del-archivo`) para vincular cada función a su archivo. Si no, las funciones se listan directamente sin subsección |
| `## Notes` | no | Decisiones técnicas relevantes o restricciones del módulo |

### Formato de `## Functions` según nivel de detalle

**Sin estructura** (solo funciones, sin vínculo a archivos):
```markdown
## Functions
- login(username, password)
- validateSession(token)
- hashPassword(password)
```

**Con estructura** (funciones vinculadas a archivos mediante subsecciones):
```markdown
## Functions

### auth-controller
- login(username, password)
- register(username, password, birthDate)

### auth-service
- validateSession(token)
- hashPassword(password)
```

El nombre de cada subsección (`### auth-controller`) debe coincidir con el `id` de un archivo declarado en `files` del frontmatter.

## Módulo de frontend

### Ubicación

```
modules/frontend/{id}-frontend-modules.md
```

### Formato completo

```markdown
---
type: module
layer: frontend
id: auth-frontend
name: Auth Views
description: Handles the login and registration UI and session state
screens: [login, register]
consumes-api: [auth-backend]
depends-on: []
folders:
  - id: views
    path: src/modules/auth/views
  - id: stores
    path: src/modules/auth/stores
files:
  - id: login-view
    folder: views
    path: LoginView.vue
    type: component
  - id: register-view
    folder: views
    path: RegisterView.vue
    type: component
  - id: auth-store
    folder: stores
    path: auth.store.js
    type: store
---

## Purpose
Explanation of what this frontend module does and what part of the UI it covers.

## State
- currentUser
- isAuthenticated
- authError
- isLoading

## Functions

### login-view
- handleLogin(username, password)
- goToRegister()

### register-view
- handleRegister(username, password, birthDate)
- goToLogin()

### auth-store
- setCurrentUser(user)
- clearSession()
- checkSession()

## Notes
Relevant technical decisions or constraints for this module.
```

### Referencia de campos del frontmatter

| Campo | Tipo | Requerido | Descripción |
|-------|------|-----------|-------------|
| `type` | string | **sí** | Siempre `module` |
| `layer` | string | **sí** | Siempre `frontend` para módulos de cliente |
| `id` | string | **sí** | Identificador único. Debe coincidir con el nombre del archivo antes de `-frontend-modules.md` |
| `name` | string | **sí** | Nombre legible del módulo |
| `description` | string | **sí** | Descripción breve en una línea |
| `screens` | lista de IDs | **sí** | IDs de pantallas que pertenecen a este módulo. Cada ID apunta a `screens/{id}-screens.md`. Puede ser lista vacía `[]` |
| `consumes-api` | lista de IDs | **sí** | IDs de módulos de backend cuya API consume este módulo. Puede ser lista vacía `[]` |
| `depends-on` | lista de IDs | **sí** | IDs de otros módulos de frontend de los que depende. Puede ser lista vacía `[]` |
| `folders` | lista de objetos | no | Subcarpetas del módulo. Cada objeto tiene `id` y `path` |
| `files` | lista de objetos | no | Archivos del módulo. Cada objeto tiene `id`, `path` y `type` (tipo de archivo: `component`, `store`, `composable`, `view`, etc.). El campo `folder` es opcional e indica el ID de la carpeta a la que pertenece; si se omite, el archivo se considera en la raíz del módulo |

### Referencia de secciones Markdown

| Sección | Requerida | Contenido |
|---------|-----------|-----------|
| `## Purpose` | **sí** | Qué hace el módulo y qué parte de la interfaz cubre |
| `## State` | no | Variables de estado principales que maneja el módulo |
| `## Functions` | no | Funciones o handlers del módulo. Igual que en backend, pueden vincularse a archivos con subsecciones o listarse directamente |
| `## Notes` | no | Decisiones técnicas relevantes o restricciones del módulo |

---

## Cómo funcionan las referencias entre archivos

Todos los valores en campos de lista como `screens`, `database`, `consumes-api` y `depends-on` son IDs que el parser usa para localizar otros archivos.

| Campo | Carpeta donde busca | Patrón de archivo |
|-------|--------------------|--------------------|
| `database` | `database/` | `{id}-database.md` |
| `screens` | `screens/` | `{id}-screens.md` |
| `consumes-api` | `modules/backend/` | `{id}-backend-modules.md` |
| `depends-on` (backend) | `modules/backend/` | `{id}-backend-modules.md` |
| `depends-on` (frontend) | `modules/frontend/` | `{id}-frontend-modules.md` |

El campo `folder` dentro de cada objeto de `files` hace referencia al `id` de una carpeta declarada en `folders` del mismo archivo.

---

## Tipos de archivo válidos

Los valores del campo `type` en los objetos de `files` no son libres. Deben declararse en el archivo `01-modules.md` del proyecto, dentro del campo `file-types`, separados por capa.

El parser usa esa lista como vocabulario de referencia. Si un tipo no está declarado, se trata como personalizado pero no provoca error.

La definición completa del formato de `01-modules.md` y la lista de tipos predefinidos está en `04.2-formato-indice-modulos.md`.

---

## Jerarquía interna del módulo

Cuando se declaran `folders` y `files`, el parser puede construir una vista detallada de la estructura interna del módulo:

```
módulo
├── carpeta (folder)
│   ├── archivo (file)
│   │   ├── función
│   │   └── función
│   └── archivo (file)
│       └── función
└── carpeta (folder)
    └── archivo (file)
        └── función
```

Esta jerarquía es completamente opcional. Si no se declaran `folders` ni `files`, el módulo se representa como un nodo único con sus funciones directamente asociadas. Si tampoco se declaran funciones, el módulo se representa solo con su información base.

## Ejemplos según nivel de detalle

### Mínimo (solo campos obligatorios)

```markdown
---
type: module
layer: backend
id: auth-backend
name: Authentication
description: Handles user identity and session management
database: [users]
api:
  - POST /auth/login
  - POST /auth/logout
depends-on: []
---

## Purpose
Manages authentication and session tokens for the application.
```

### Medio (con funciones, sin estructura interna)

```markdown
---
type: module
layer: backend
id: auth-backend
name: Authentication
description: Handles user identity and session management
database: [users]
api:
  - POST /auth/login
  - POST /auth/register
  - POST /auth/logout
  - GET /auth/me
depends-on: []
---

## Purpose
Manages authentication and session tokens for the application.

## Functions
- login(username, password)
- register(username, password, birthDate)
- logout(token)
- validateSession(token)
```

### Completo (con estructura interna de carpetas, archivos y funciones vinculadas)

```markdown
---
type: module
layer: backend
id: auth-backend
name: Authentication
description: Handles user identity, session management and access control
database: [users]
api:
  - POST /auth/login
  - POST /auth/register
  - POST /auth/logout
  - GET /auth/me
depends-on: []
folders:
  - id: controllers
    path: src/controllers
  - id: services
    path: src/services
files:
  - id: auth-controller
    folder: controllers
    path: auth.controller.js
    type: controller
  - id: auth-service
    folder: services
    path: auth.service.js
    type: service
---

## Purpose
Centralizes all logic related to user authentication. Validates credentials,
creates and revokes session tokens, and exposes the current user data to
other modules that need it.

## Functions

### auth-controller
- login(username, password)
- register(username, password, birthDate)
- logout(token)

### auth-service
- validateSession(token)
- hashPassword(password)
- generateToken(userId)

## Notes
Passwords are always hashed with bcrypt before storage.
Session tokens are JWT with a 24-hour expiry.
```
